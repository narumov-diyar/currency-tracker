## Этап 1. Определение проблемы и формулировка темы

**Проблема.** Пользователь, следящий за несколькими криптовалютами, вынужден открывать отдельную страницу для каждой интересующей пары и вручную сопоставлять их динамику за разные интервалы времени. Курс одного актива относительно другого в большинстве сервисов не отображается и требует самостоятельного пересчёта. Набор отслеживаемых пар не сохраняется между сеансами и устройствами.

**Тема.** Веб-сервис «Трекер курсов криптовалют»: персональный список криптовалютных пар с отображением текущего курса, кросс-курса, истории изменений в виде графика, сравнения динамики двух активов пары и пользовательских оповещений о достижении заданного курса. Поддерживаются только криптовалютные активы, котируемые в USDT; фиатные валюты в состав решения не входят. Источник данных — публичное API биржи Bybit.

## Этап 2. Выработка требований

### Пользовательские сценарии

Сервер хранит и отдаёт цену каждого актива отдельно, в USDT (BTC → USDT, ETH → USDT и т. д.), а не цену каждой возможной пары. Кросс-курс пары вычисляется на клиенте делением одного полученного ряда на другой.

**US-1. Персональный список отслеживания.** Как пользователь, я хочу зарегистрироваться и вести список интересующих меня криптопар, чтобы не подбирать их заново при каждом обращении к сервису и на разных устройствах.

Критерии приёмки:

- Регистрация выполняется по адресу электронной почты и паролю; адрес уникален, пароль хранится в виде хеша; обращение к защищённым разделам без аутентификации возвращает код 401.
- Пара добавляется из справочника поддерживаемых активов и не может быть добавлена повторно одному пользователю; удаление пары из списка пользователя не затрагивает историю котировок в общем хранилище.
- Для каждой пары отображаются курс, изменение за выбранный период и время последнего обновления; при отсутствии обновления свыше 5 минут данные помечаются как устаревшие и не скрываются.

**US-2. Анализ курса: история и реальное время.** Как пользователь, я хочу просматривать график выбранной пары с переключением периода (1h, 4h, 1d, 1w, реальное время) и режима отображения, чтобы оценивать динамику курса в требуемом масштабе времени.

Критерии приёмки:

- Смена периода перерисовывает график по данным хранилища без обращения к бирже; отсутствие данных за период отображается как пустое состояние.
- В режиме «Сравнение динамики» активы пары отображаются отдельными кривыми с независимыми осями Y; при наведении курсора ближайшая кривая выделяется и отображается свечами (OHLC), вторая кривая становится полупрозрачной.
- В режиме «Кросс-курс» отображается одна кривая с одной осью Y, вычисляемая на клиенте из загруженных рядов без дополнительного запроса к серверу.
- Вкладка «Реальное время» (15 минут) обновляет график по мере поступления котировок с частотой до одного обновления в секунду; поступающие котировки в базу данных не записываются.

**US-3. Оповещения о достижении целевого курса.** Как пользователь, я хочу задавать пороговое значение курса актива в USDT, чтобы получать оповещение при его достижении без постоянного наблюдения за графиком.

Критерии приёмки:

- Правило содержит актив, направление («выше», «ниже») и целевое значение курса в USDT; пользователь просматривает, изменяет и удаляет собственные правила.
- Правило хранится в базе данных и действует независимо от наличия открытого сеанса пользователя.
- Проверка правил выполняется сервером при сохранении каждого нового минутного снимка цены; правило считается сработавшим при пересечении порога между двумя соседними снимками, а не при точном совпадении цены с пороговым значением.
- После срабатывания правило переводится в состояние «сработало», оповещение формируется однократно.

**US-4. Относительная динамика пары.** Как пользователь, я хочу видеть, какой из двух активов пары изменился сильнее за выбранный период, чтобы оценивать относительную силу активов внутри пары.

Критерии приёмки:

- Для выбранного периода отображается изменение каждого актива пары в процентах и разность между этими значениями.
- Значения вычисляются на клиенте по загруженным для графика рядам без дополнительного запроса к серверу и пересчитываются при смене периода или пары.
- При отсутствии данных по одному из активов за выбранный период вместо сравнения отображается признак недостаточности данных.

### Масштаб системы

Исходные допущения расчёта:

| Параметр | Обозначение | Значение | Основание |
|---|---|---|---|
| Уникальных пользователей в сутки | `U` | 10 000 | задано условием |
| Сессий на пользователя в сутки | `S` | 2 | типовой профиль использования сервиса мониторинга курсов |
| Длительность сессии | `T` | 300 с | среднее время просмотра дашборда за одно обращение |
| Интервал автообновления списка | `r` | 60 с | периодичность обновления курса на клиенте |
| Обращений за историей за сессию | `h` | 2 | первичная загрузка графика и одна смена периода |
| Доля пользователей, изменяющих список за сутки | `f` | 0,2 | доля активно редактирующих список пользователей |
| Изменений списка у этой группы | `e` | 1,5 | среднее число операций добавления и удаления за сутки |
| Коэффициент пиковой нагрузки | `k` | 4 | отношение пиковой часовой нагрузки к средней |
| Активов в каталоге сборщика | `A` | 30 | число отдельных отслеживаемых активов |
| Интервал опроса биржи сборщиком | `p` | 60 с | периодичность обновления снимков цены |
| Среднее число пар в списке пользователя | `W` | 5 | типовой размер персонального списка |

Нагрузка от пользовательских запросов:

```
sessions_per_day      = U × S                = 20 000
refreshes_per_session = ceil(T / r)          = 5
watchlist_requests    = 20 000 × 5           = 100 000
auth_requests         = 20 000 × 1           = 20 000
history_requests      = 20 000 × h           = 40 000
edit_requests         = U × f × e            = 3 000
total_requests                               = 163 000

avg_rps  = total_requests / 86 400 ≈ 1,9 запроса/с
peak_rps = avg_rps × k             ≈ 7,5 запроса/с
```

С учётом кратковременных всплесков расчётный потолок системы принимается равным 15–20 запросам/с. Основную часть нагрузки составляют операции чтения; доля пользовательской записи составляет около 2 % от общего числа запросов.

Нагрузка от сборщика данных не зависит от числа пользователей, так как опрашивается каждый актив каталога, а не каждая пользовательская пара:

```
polling_cycles    = 86 400 / p            = 1 440
snapshots_per_day = polling_cycles × A    = 43 200
avg_write_rps     = snapshots_per_day / 86 400 = 0,5 записи/с
```

Объём записываемых данных. Раз в 60 секунд для каждого актива запрашивается эндпоинт `GET /v5/market/kline` (`category=spot`, `interval=1`, `limit=2`) и сохраняется последняя закрытая минутная свеча. Сохраняются семь значений свечи: `startTime` → `collected_at` (timestamptz, 8 байт), `openPrice`, `highPrice`, `lowPrice`, `closePrice` → numeric(18,8) (по 10 байт), `volume` и `turnover` → numeric(24,8) (по 12 байт); дополнительно `id` (bigserial, 8 байт) и `asset_id` (int, 4 байта). Размер строки составляет 76 байт данных, с заголовком кортежа PostgreSQL — около 105 байт, с записью индекса `(asset_id, collected_at)` — около 145 байт.

```
daily_volume   = snapshots_per_day × 145 байт ≈ 6,3 МБ/сутки
monthly_volume ≈ 189 МБ/месяц
yearly_volume  ≈ 2,3 ГБ/год
```

Объём записи не зависит от числа пользователей и изменяется только при расширении каталога активов `A` или уменьшении интервала опроса `p`. Котировки, поступающие по потоковому каналу для вкладки «Реальное время», не сохраняются: сборщик подписан на публичный WebSocket-топик `tickers.<ASSET>USDT`, использует из сообщения значения `lastPrice` и `ts`, хранит последнее значение в оперативной памяти и передаёт его подключённым клиентам с ограничением не чаще одного сообщения в секунду на пару. Таблица правил оповещений (`user_id`, `asset_id`, `direction`, `target_price_usdt`, `status`) на порядки меньше таблицы снимков и в оценке объёма хранения не учитывается.

Объём сетевого трафика. Периоды 1h, 4h, 1d, 1w формируются выборкой минутных свечей за соответствующее окно времени без агрегации в более крупные интервалы, поэтому объём ответа определяется длиной периода. Ответ на запрос списка при `W = 5` составляет около 0,7 КБ, что даёт около 70 МБ/сутки. Объём ответа на запрос истории при 90 байтах на свечу и двух активах пары:

| Период | Свечей на актив | Свечей на пару | Объём ответа |
|---|---|---|---|
| 1h | 60 | 120 | ≈ 11 КБ |
| 4h | 240 | 480 | ≈ 43 КБ |
| 1d | 1 440 | 2 880 | ≈ 259 КБ |
| 1w | 10 080 | 20 160 | ≈ 1,8 МБ |

```
history_payload_avg = 11 КБ + (43 + 259 + 1 814) КБ / 3 ≈ 716 КБ/сессию
history_traffic     = sessions_per_day × 716 КБ         ≈ 14,3 ГБ/сутки
read_traffic        ≈ 14,4 ГБ/сутки без сжатия
```

При включении сжатия HTTP фактический объём составляет около 2–3 ГБ/сутки. В отличие от объёма записи, объём чтения прямо пропорционален числу пользователей и при увеличении нагрузки до 100 000 пользователей в сутки возрастает приблизительно в десять раз.

Для 10 000 пользователей в сутки достаточно одного экземпляра сервера приложения, одной базы данных PostgreSQL и одного процесса-сборщика. Ограничивающими факторами на этом масштабе являются объём отдаваемого пользователям трафика и ограничения биржи на частоту запросов, а не объём записи или вычислительная нагрузка.

### Отказоустойчивость

Внешняя зависимость — публичное API биржи Bybit. Рассматриваемые виды отказов: превышение времени ожидания, ошибка 429 (превышение лимита запросов), ошибки 5xx, невалидный ответ, разрыв сетевого соединения. С биржей взаимодействует только сборщик; пользовательские запросы обслуживаются сервером приложения и от доступности биржи не зависят.

**Кэширование.** Каждый успешно полученный снимок цены сохраняется в базе данных вместе со временем получения и служит единственным источником данных для пользовательских запросов. Ошибка очередного цикла опроса не изменяет последний сохранённый снимок.

**Деградация функций.**

| Функция | Биржа доступна | Биржа недоступна |
|---|---|---|
| Регистрация, вход, список пользователя | без изменений | без изменений |
| Текущий курс актива | обновляется раз в минуту | последний сохранённый снимок с пометкой «устарело» |
| График за период 1h, 4h, 1d, 1w | пополняется новыми точками | строится по сохранённым свечам без новых точек |
| Кросс-курс и относительная динамика | вычисляются по актуальным рядам | вычисляются по последним сохранённым рядам |
| Вкладка «Реальное время» | котировки передаются по мере поступления | отображается последняя полученная котировка с пометкой о задержке |
| Оповещения | правило проверяется при каждом новом снимке | проверка приостанавливается, правила сохраняются и проверяются после восстановления |
| Актив без сохранённых снимков | курс появляется после первого успешного цикла | состояние «нет данных» без ошибки страницы |

Полный отказ сервиса при недоступности биржи не допускается. Единственным допустимым случаем пустого экрана является отсутствие в базе данных снимков, например при первом запуске системы в условиях недоступной биржи.

**Повторные попытки.** Повтор выполняется только при временных ошибках (превышение времени ожидания, 429, 5xx) с возрастающей паузой 1 с → 2 с → 4 с и ограничением числа попыток и общего времени цикла. Ошибки конфигурации к повторным попыткам не приводят. После исчерпания попыток цикл завершается без изменения последнего сохранённого снимка, причина отказа фиксируется в журнале.

**Circuit Breaker.**

| Состояние | Поведение |
|---|---|
| Closed | опрос биржи выполняется по расписанию |
| Open | обращения к бирже приостановлены на фиксированный интервал, в базе данных сохраняются последние снимки |
| Half-open | выполняется один пробный запрос: при успехе — переход в Closed, при отказе — возврат в Open |

Переход в состояние Open выполняется после нескольких последовательных неуспешных циклов опроса. Circuit Breaker реализован в сборщике; сервер приложения к бирже не обращается.

**Таймауты и изоляция.** HTTP-клиент сборщика использует фиксированное время ожидания запроса. Сборщик выполняется отдельным процессом, его отказ или переход в состояние Open не влияет на работу сервера приложения и базы данных.
