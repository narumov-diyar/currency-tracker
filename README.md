# Этап 2. Выработка требований

**Проект:** трекер курсов валют

**Дисциплина:** конструирование программного обеспечения

Тема: веб-сервис «Трекер курсов валют» — пользователь собирает список интересующих его валютных и криптопар и в одном интерфейсе видит их текущий курс, кросс-курс и историю изменений в виде графика.

Архитектурное решение: сервер хранит и отдаёт цену каждого актива отдельно, в USDT (BTC → USDT, ETH → USDT и т.д.), а не цену каждой возможной пары. Кросс-курс произвольной пары (например, сколько BTC за 1 ETH) клиент вычисляет самостоятельно делением одного полученного ряда на другой. Источником данных является публичное API биржи Bybit — оттуда получены как текущая цена, так и исторические свечи (OHLC).

---

## 1. Пользовательские сценарии

### US-1. Регистрация
Как гость, я хочу зарегистрироваться по email и паролю, чтобы мой список пар сохранялся между сессиями и устройствами.

**Критерии приёмки:**
- Email уникален; повторная регистрация с тем же email отклоняется с понятной ошибкой.
- Пароль хранится только в виде хеша.
- После успешной регистрации пользователь сразу считается вошедшим в систему.

### US-2. Вход
Как зарегистрированный пользователь, я хочу войти в аккаунт, чтобы увидеть свой сохранённый watchlist, а не пустой список гостя.

**Критерии приёмки:**
- При верных данных открывается дашборд с ранее сохранённым списком.
- При неверных данных система не сообщает, существует ли такой email — только общее сообщение об ошибке.
- Запрос к защищённым разделам без входа возвращает ошибку 401.

### US-3. Добавление пары в watchlist
Как пользователь, я хочу добавить пару из двух активов, чтобы отслеживать её курс на боковой панели.

**Критерии приёмки:**
- Оба актива пары выбираются из справочника поддерживаемых активов.
- Одна и та же пара не может быть добавлена дважды одному пользователю.
- Пара сразу появляется в watchlist с курсом, вычисленным из уже известных серверу USDT-цен, или с пометкой «нет данных», если по одному из активов ещё не было ни одного снимка.

### US-4. Удаление пары
Как пользователь, я хочу убрать пару из watchlist, чтобы на панели оставалось только нужное.

**Критерии приёмки:**
- После удаления пара пропадает из watchlist пользователя.
- Исторические данные по активам пары в общей базе не удаляются.

### US-5. Watchlist на боковой панели
Как пользователь, я хочу видеть узкую боковую панель со списком своих пар, курсом, изменением за период и временем обновления.

**Критерии приёмки:**
- По каждой паре отображается: название пары, курс, процент изменения за выбранный период (зелёным — рост, красным — падение), время последнего обновления.
- Клик по паре открывает её на основном дашборде.
- Внизу панели — кнопка «Добавить пару».
- Пустой список отображается как пустое состояние с предложением добавить первую пару.

### US-6. Свежесть данных
Как пользователь, я хочу видеть, что курс мог устареть, чтобы понимать, можно ли на него опираться.

**Критерии приёмки:**
- Рядом с курсом отображается время последнего обновления в едином формате.
- Если данные старше порога свежести (5 минут), интерфейс помечает их как устаревшие, не скрывая.

### US-7. График и переключение периода
Как пользователь, я хочу открыть основной график по выбранной паре и переключать период (1h / 4h / 1d / 1w), чтобы оценить динамику курса на разных масштабах времени.

**Критерии приёмки:**
- В правом верхнем углу дашборда расположен переключатель периодов 1h, 4h, 1d, 1w.
- При смене периода график перерисовывается по историческим данным из хранилища, без обращения к бирже в момент клика.
- Отсутствие данных за период отображается как пустое состояние, без падения страницы.

### US-8. Режим «Сравнение динамики» (dual Y-axis)
Как пользователь, я хочу видеть две кривые пары на одном графике с двумя независимыми вертикальными осями, чтобы сравнивать их динамику при разном масштабе цены.

**Критерии приёмки:**
- Каждый актив пары отображается своей кривой и своим цветом.
- У каждой кривой — своя ось Y (левая и правая).
- При наведении курсора на график ближайшая к курсору кривая выделяется и отображается свечами (OHLC) в окрестности точки наведения, вторая кривая становится полупрозрачной; рядом с курсором отображаются точное значение и время.

### US-9. Режим «Кросс-курс»
Как пользователь, я хочу переключиться в режим, где вместо двух кривых показывается одна — курс одного актива пары к другому.

**Критерии приёмки:**
- Кросс-курс вычисляется на клиенте делением уже полученных USDT-рядов двух активов пары; переключение режима не создаёт новый запрос к серверу, если данные за выбранный период уже загружены.
- График отображает одну кривую с одной осью Y.
- При наведении курсора отображаются точное значение кросс-курса и время снимка.

### US-10. Работа при недоступности внешнего источника курсов
Как пользователь, я хочу видеть последний известный курс и историю, даже если биржа временно недоступна, чтобы сервис оставался полезным.

**Критерии приёмки:**
- Ответ пользователю не зависит от доступности биржи в текущий момент.
- Поведение при сбое описано в разделе «Отказоустойчивость».

## 2. Масштаб системы: нагрузка от 10 000 пользователей в сутки

### 2.1. Структура пользовательского сеанса

За один сеанс пользователь выполняет:
1. Один запрос на вход / проверку сессии.
2. Периодические обновления watchlist в течение сессии; сервер отдаёт все цены пользователя одним запросом независимо от числа пар в списке.
3. Один-два запроса за историей (свечами) для графика: при открытии дашборда и при смене периода.
4. Переключение режима «Сравнение динамики» / «Кросс-курс» не создаёт сетевой запрос — кросс-курс вычисляется на клиенте из уже загруженных данных.
5. Добавление или удаление пары.

### 2.2. Допущения

| Параметр | Обозначение | Значение | Основание |
|---|---|---|---|
| Уникальных пользователей в сутки | `U` | 10 000 | задано условием |
| Сессий на пользователя в сутки | `S` | 2 | типовой профиль использования сервиса мониторинга курсов |
| Длительность сессии | `T` | 300 с (5 мин) | среднее время просмотра дашборда за один заход |
| Интервал автообновления watchlist | `r` | 60 с | периодичность обновления курса на клиенте |
| Обращений за историей за сессию | `h` | 2 | первичная загрузка графика и одна смена периода |
| Доля пользователей, меняющих список за сутки | `f` | 0.2 | доля активно редактирующих watchlist пользователей |
| Изменений списка у редактирующих пользователей | `e` | 1.5 | среднее число операций добавления/удаления за сутки у этой группы |
| Коэффициент пиковой нагрузки | `k` | 4 | отношение пиковой часовой нагрузки к средней |
| Активов в каталоге сборщика | `A` | 30 | число отдельных отслеживаемых активов |
| Интервал опроса биржи сборщиком | `p` | 60 с | периодичность обновления снимков цены |

### 2.3. Расчёт запросов к API

Число сессий в сутки:

```
sessions_per_day = U × S = 10 000 × 2 = 20 000
```

Число обновлений watchlist за одну сессию, включая начальную загрузку:

```
refreshes_per_session = ceil(T / r) = ceil(300 / 60) = 5
```

Запросы watchlist в сутки:

```
watchlist_requests = sessions_per_day × refreshes_per_session
                    = 20 000 × 5 = 100 000
```

Запросы входа / проверки сессии в сутки:

```
auth_requests = sessions_per_day × 1 = 20 000
```

Запросы истории (свечей) в сутки:

```
history_requests = sessions_per_day × h = 20 000 × 2 = 40 000
```

Запросы на изменение watchlist в сутки:

```
edit_requests = U × f × e = 10 000 × 0.2 × 1.5 = 3 000
```

Итого запросов к API в сутки:

```
total_requests = watchlist_requests + auth_requests + history_requests + edit_requests
               = 100 000 + 20 000 + 40 000 + 3 000
               = 163 000
```

### 2.4. Средняя и пиковая нагрузка

Средняя интенсивность запросов:

```
avg_rps = total_requests / 86 400 = 163 000 / 86 400 ≈ 1.9 запроса/с
```

Пиковая интенсивность с учётом коэффициента `k`:

```
peak_rps = avg_rps × k ≈ 1.9 × 4 ≈ 7.5 запроса/с
```

С учётом кратковременных всплесков нагрузки расчётный потолок системы принимается равным 15–20 запросам/с. Основная часть нагрузки — операции чтения (watchlist и история); доля пользовательской записи (`edit_requests`) составляет около 2% от общего числа запросов.

### 2.5. Нагрузка от сборщика данных

Сборщик обращается к бирже независимо от числа пользователей: он забирает цену каждого актива каталога `A`, а не каждой пользовательской пары.

Циклов опроса в сутки:

```
polling_cycles = 86 400 / p = 86 400 / 60 = 1 440
```

Записей (снимков цены) в сутки:

```
snapshots_per_day = polling_cycles × A = 1 440 × 30 = 43 200
```

Средняя write-нагрузка сборщика:

```
avg_write_rps = snapshots_per_day / 86 400 = 43 200 / 86 400 = 0.5 записи/с
```

### 2.6. Вывод

```
avg_rps (пользователи)  ≈ 1.9 запроса/с      peak_rps ≈ 7.5–20 запросов/с
avg_write_rps (сборщик) ≈ 0.5 записи/с
```

Для 10 000 пользователей в сутки достаточно одного инстанса API, одной базы PostgreSQL и одного процесса-сборщика. Ограничивающим фактором на этом масштабе являются лимиты биржи на частоту запросов и объём хранимой истории свечей, а не вычислительная нагрузка от пользователей.

## 3. Отказоустойчивость при недоступности внешнего источника курсов

Внешняя зависимость — публичное API биржи Bybit, откуда получены текущая цена и исторические свечи. Возможные сбои: таймаут, ошибка 429 (превышение лимита запросов), ошибка 5xx, невалидный ответ, разрыв сети.

Принцип: с биржей взаимодействует только сборщик; пользователи взаимодействуют только с сервером системы.

### 3.1. Кэширование
Каждый успешно полученный снимок цены актива сохраняется в базе данных вместе со временем получения (`collected_at`). Это единственный источник данных для пользовательских запросов; watchlist и график не обращаются к бирже напрямую. Ошибка очередного опроса не изменяет последний сохранённый снимок.

### 3.2. Деградация функций при сбое

| Функция | Биржа доступна | Биржа недоступна |
|---|---|---|
| Регистрация, вход, watchlist | без изменений | без изменений |
| Текущий курс актива | обновляется раз в минуту | последний сохранённый снимок, время и пометка «устарело» |
| График (свечи за 1h/4h/1d/1w) | пополняется новыми точками | строится по сохранённым свечам, без новых точек |
| Кросс-курс | вычисляется на клиенте из актуальных рядов | вычисляется на клиенте из последних сохранённых рядов |
| Новый актив без сохранённых снимков | курс появляется после первого успешного цикла опроса | статус «нет данных», без ошибки страницы |

Полный отказ сервиса из-за недоступности биржи не допускается. Единственный допустимый случай пустого экрана — отсутствие в базе данных ни одного снимка, например при первом запуске системы в условиях недоступной биржи.

### 3.3. Повторные попытки (retry)
- Повтор выполняется только при временных ошибках (таймаут, 429, 5xx).
- Между попытками применяется возрастающая пауза (1 с → 2 с → 4 с) с ограничением числа попыток и общего времени цикла.
- Ошибки конфигурации не приводят к повторным попыткам.
- После исчерпания попыток цикл завершается без изменения последнего сохранённого снимка; причина сбоя фиксируется в логах.

### 3.4. Circuit Breaker

| Состояние | Поведение |
|---|---|
| Closed | опрос биржи выполняется по расписанию |
| Open | обращения к бирже приостановлены на фиксированный интервал; в базе остаются последние снимки |
| Half-open | выполняется один пробный запрос: успех — переход в Closed, неуспех — возврат в Open |

Переход в состояние Open происходит после нескольких подряд неуспешных циклов опроса. Circuit Breaker реализован в сборщике; сервер, обслуживающий пользователей, к бирже не обращается.

### 3.5. Таймауты и изоляция
- HTTP-клиент сборщика использует фиксированный таймаут запроса.
- Сборщик выполняется отдельным процессом: его сбой или переход в состояние Open не влияет на работу API и базы данных.
- Пользовательский запрос не зависит от ответа биржи.

### 3.6. Логика поведения при сбое
1. В штатном режиме сборщик обновляет снимки цен каждую минуту, пользователи читают данные из базы.
2. При сбоях биржи выполняется повтор запроса с возрастающей паузой.
3. При продолжительных сбоях активируется Circuit Breaker, обращения к бирже приостанавливаются.
4. Пользователь получает последний известный курс, историю и кросс-курс, рассчитанный на последних доступных данных, с пометкой об устаревании.
5. При восстановлении доступности биржи: Half-open → Closed → возобновление обновления снимков и графика.
