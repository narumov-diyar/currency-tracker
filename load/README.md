# Этап 5. Нагрузка и сборщик

## Запуск

Из корня репозитория, с запущенным Docker и Docker Compose v2.

```bash
bash scripts/test.sh
bash scripts/load.sh browser
bash scripts/load.sh all
bash scripts/load.sh soak
```

`all` запускает L-1–L-4. L-1 держит 7,5 и 20 запросов/с по 5 минут,
L-2 повышает нагрузку на чтение до 360 запросов/с, L-3 отдельно нагружает
вход и регистрацию, L-4 держит 70 и 300 зрителей по минуте. `soak` запускает
отдельный 30-минутный L-5 с 20 запросами/с и журналом планировщика Go.
Можно запустить один сценарий по имени: `mix`, `capacity`, `auth`, `websocket`.
Если ступень чтения в 360 запросов/с проходит, верхнюю ступень следующего
замера можно задать через `LOAD_MAX_RATE`.

Стенд заново наполняет PostgreSQL за 8 дней, запускает свёртку и проверяет
непустые ряды `1h`, `4h`, `1d` и `1w`. В сценарии смеси по умолчанию
200 тестовых пользователей с пятью парами. Для WebSocket отдельный генератор
посылает уведомления PostgreSQL по восьми активам каждые 50 мс.
Сборщик и внешние источники в нагрузочном стенде не используются.
Контейнеры и временный том удаляются при выходе. JSON, снимки ресурсов,
журнал генератора и trace при падении браузера сохраняются в
`load/results/<имя-запуска>/`. В CI проверка браузера запускается автоматически,
короткая проверка k6 включена для ручного запуска workflow.

## Замер 25 ноября 2026 года

Docker Linux/aarch64, 2 логических CPU и 1,91 ГиБ RAM. API, PostgreSQL и k6
работали на одном хосте в сети Docker. На этой машине параллельно работало
демо проекта. Задержки HTTP включают локальное обращение к API и передачу
ответа внутри Docker. В бюджетах README на передачу истории отводится
около 85 мс на канале 5 Мбит/с. Такой канал в замере не моделировался,
отдельного замера чистого времени обработки запроса в Go нет.

```bash
LOAD_QUICK=1 LOAD_USERS=20 LOAD_MIX_SECONDS=30 LOAD_WS_SECONDS=15 bash scripts/load.sh all
```

### L-1. Смесь запросов

| Метод | Бюджет p95, мс | p95 / p99 при 7,5, мс | rps | p95 / p99 при 20, мс | rps |
|---|---:|---:|---:|---:|---:|
| `GET /api/watchlist` | 150 | 3,93 / 10,23 | 4,30 | 57,84 / 89,65 | 12,93 |
| `GET /api/history` | 400 | 18,88 / 27,58 | 2,17 | 161,64 / 288,15 | 4,20 |
| `POST /api/auth/login` | 300 | 429,18 / 436,95 | 0,80 | 925,12 / 1 214,93 | 2,50 |

Rps рассчитаны по числу запросов каждого метода за 30 секунд соответствующей
ступени. Обе ступени завершились без HTTP-ошибок и пропусков итераций.
Короткий режим выполняет и правки пар и правил, а отдельные пороги для каждого
редкого метода включены в полном профиле. Замер чтения уложился в проектный
бюджет. Смесь завершилась с ошибкой порога входа на обеих ступенях.

### L-2 и L-3. Пределы чтения и аутентификации

При 360 запросах/с чтения получено 2 161 запрос за 6 секунд плато.
Для истории p95/p99 составили 5,18/8,81 мс, ошибок и пропущенных итераций
не было. Предел чтения на этом коротком замере лежит за последней ступенью.

| Метод | p95 при 1 rps, мс | p95 при 2 rps, мс | p95 при 8 rps, мс | Пропуски при 8 rps |
|---|---:|---:|---:|---:|
| Вход | 415,45 | 294,02 | 6 091,41 | 14 |
| Регистрация | 286,11 | 642,80 | 5 043,56 | 11 |

При 8 попытках/с тестовый клиент уже пропускал итерации. На ступени в районе
проектного пика около 1 запроса/с бюджет входа также нарушился. Результат
на 2 запросах/с основан всего на 13 входах, поэтому устойчивый потолок
в рамках бюджета из этого замера вывести нельзя. При высокой нагрузке на
аутентификацию в снимке API использовал 104,54% CPU, PostgreSQL — 0,10%,
его четыре соединения были свободны. Вместе с результатом L-2 это указывает
на хеширование паролей bcrypt в API как первое узкое место на этом стенде.

### L-4 и L-5. Поток и длительная нагрузка

| Одновременные клиенты | Доставка p95 / p99, мс | Получено тиков | Ошибки потока |
|---|---:|---:|---:|
| 70 | 49 / 50 | 1 028 | 0 |
| 300 | 49 / 51 | 4 479 | 0 |

В обоих замерах соседних тиков с интервалом отправки менее 850 мс не было.
Допуск учитывает период генератора и работу планировщика. По снимкам API
использовал около 8–10 МиБ до ступени в 300 клиентов и до 22 МиБ при ней
и сразу после неё. Эти короткие замеры показывают расход памяти при
подключениях. Для вывода о росте памяти со временем нужен длительный прогон.
Пятиминутные ступени L-1, полные профили L-2–L-4 и 30 минут L-5 ещё предстоит
замерить.

## Сборщик и интерфейс

- HTTP-тесты закрепляют классификацию ответов и исключений aiohttp.
- Интеграционные тесты с PostgreSQL проверяют транзакцию на пакет свечей,
  отсутствие дублей и доставку уведомлений после фиксации данных.
- Тесты сначала воспроизвели ошибки разбора. ЦБ пропускает дату из будущих
  суток UTC, криптокотировки проверяются на диапазоны хранения, ошибочная
  валюта er-api пропускается с предупреждением.
- С PostgreSQL прошли 166 тестов сборщика, покрытие рабочего кода Python — 91%.
  Для повторного замера из корня с заданным `TEST_DATABASE_URL` выполнить
  `python -m pytest collector --cov=collector --cov-report=` и
  `python -m coverage report --omit '*/tests/*'`.
- Тест Playwright прошёл в Chrome с локальными API и PostgreSQL. Он проверяет
  регистрацию, добавление BTC/USDT, сохранение пары после повторного входа
  и появление правила в списке. Контейнерный запуск предназначен для Linux и CI.
